## Editor capability matrix

The source of truth is
`backend/api/crates/wakaclock-core/src/ai/editor_capability.rs`.

| Surface | Current implementation | Input evidence | AI provenance | Safe interpretation |
| --- | --- | --- | --- | --- |
| VS Code | Implemented | editor input window | metadata sidecar/native adapter | Can correlate only when the sidecar or native event supplies proof; the editor name alone is insufficient. |
| Zed | Implemented through LSP | generic document change | none | Open/change/save is editor activity; it does not prove who wrote the change. |
| JetBrains | Inventory only | none | none | No support claim until a plugin or explicit producer is surveyed and tested. |
| Neovim | Inventory only | none | none | Generic autocmd/LSP events are not AI provenance. |
| Generic LSP | Inventory only | generic document change | none | LSP is a transport; an AI hook or transcript must supply authorship separately. |

The catalog deliberately exposes capability and provenance as different fields. The
same source is available through `wakaclock ai capabilities --json`, so setup and
diagnostics do not maintain a second editor matrix. A future plugin can add a native
AI producer without changing the generic editor-input classification, and a generic
LSP client cannot become verified merely by changing its display name.

## Browser paste boundary

The VS Code clipboard tracker records metadata-only counts for same-file,
same-workspace and external/unknown paste origins. It never stores clipboard contents.
The browser extension does not currently provide a trusted source-to-file provenance
event. Therefore browser paste remains `unknown` authorship until a separate explicit
integration supplies a bounded provenance token and its own consent/retention policy.

No browser permission expansion is implied by this phase. Commit authors, page titles,
clipboard text, and model names are not accepted as proof that a pasted line was
generated by AI.
