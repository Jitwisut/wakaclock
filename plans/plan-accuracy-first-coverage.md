# Plan — WakaTime-style accuracy-first coverage

**Status: proposed 2026-09-04, no code written.** Implements the direction set in
[`decision-accuracy-over-coverage.md`](decision-accuracy-over-coverage.md). Read
that file first; this one answers "so what do we actually build".

---

## 1. The core reframe: WakaTime has three mechanisms, not one

The mistake in reading WakaTime as "just native hooks" is that their 15 supported
tools do not run the same way, so they cannot share one integration. Sorting by
*how the agent executes* produces three categories, each with its own mechanism —
and this is the axis the whole plan is organised on.

| Category | How the agent runs | Mechanism that names the agent | AtoAxis today |
|---|---|---|---|
| **A. CLI agent** — Claude Code, Codex, Gemini CLI, Kilo, Kimi, Copilot CLI, OpenCode, Goose | Own process, own config dir | Native hook / plugin the tool invokes on edit | ✅ claude-code, codex `Verified` |
| **B. Editor-extension agent** — Cline, Roo Code, Continue, Cody | Inside VS Code, edits via the VS Code API | **Transcript / task-state parsing** (the extension's own history files) | ❌ all `Unverified`, `no_hooks()` |
| **C. Editor fork with built-in AI** — Cursor, Windsurf, Qoder, Kiro, Antigravity | The editor *is* the agent | The fork's own hook API, where it has one | ⚠️ cursor `Scaffold` only |

## 2. The line accuracy-first actually draws

This is the most important point in the plan, and it is easy to get wrong.

"Accuracy-first" does **not** mean "native hooks only". `wakaclock-core`'s own
model already says so — `EvidenceKind::is_verified_ai_edit()` returns true for
three kinds:

```rust
Self::NativeHook | Self::StructuredMcp | Self::CompletedTranscriptToolCall
```

A **completed transcript tool call is verified-tier evidence**, because the
agent's own transcript states which agent made which edit. That is a record, not
a guess. The two kinds that are guesses — and the only two this decision rules
out of production attribution — are:

- `FilesystemObserver` — "a file changed near an agent"
- `SessionProcessObserver` — "an agent process was alive in this workspace"

**So the line is: transcript parsing is in, filesystem/process inference is out.**
That matters enormously for scope, because it means Category B (Cline, Roo Code,
Continue — none of which expose a hook API) is reachable *without* violating the
accuracy policy, using parser infrastructure this repo already has
(`ai/parser.rs`'s `AiActivityParser` + `ParserCursor`, `ai/state.rs`'s
delivered-event dedup, proven by `claude.rs` / `codex.rs` / `gemini.rs`).

## 3. Where WakaTime is actually weak — the opening

WakaTime's marketing lists Cursor and Copilot, but their own tracker says the
in-editor case does not work:

- [vscode-wakatime#476](https://github.com/wakatime/vscode-wakatime/issues/476) —
  "code generated by AI tools (Cursor, GitHub Copilot) is being logged to
  WakaTime and counted as human coding activity." Closed with no mechanism
  documented.
- [vscode-wakatime#483](https://github.com/wakatime/vscode-wakatime/issues/483) —
  WakaTime attributes Cursor activity to VS Code and does not detect its AI
  changes.

Root cause is structural: the VS Code extension API does **not** tell you which
extension authored a document change, so an in-editor extension cannot attribute
an edit to Cline vs Copilot vs the human by watching the document. WakaTime's
editor plugin is stuck there. Categories B and C route around it — B by reading
the agent's own transcript, C by using the fork's hook API — which is why
Phase 2 and Phase 3 below are the differentiated work, not the catch-up work.

## 4. Phases

Ordered by (value × confidence) ÷ cost. Sizes are relative, not hour estimates.

### Phase 0 — Make the policy enforceable, not just documented — **S**

Today "we never ship inferred attribution" rests on a default (`ObserverConfig`
`enabled=false`) that one config file flips. Close that:

- **P0.1** Ensure an inferred verdict can never carry an agent name to the
  dashboard. Either drop `AttributionMode::Infer` from the deserialised config
  surface, or keep it but assert at the emit boundary that `ai_inferred` rows
  have `ai_agent = NULL`. Prefer the second — it preserves the shadow-research
  path while making a mislabelled agent structurally impossible.
- **P0.2** Frontend: `ai_inferred` / `unknown` must not render in the "which AI"
  table as if they were an identified agent. This is the open follow-up left
  unanswered in the decision doc — decide *show as a separate "unattributed"
  bucket* vs *hide entirely* before building.
- **P0.3** One regression test that fails if an `ai_inferred` heartbeat ever
  carries a non-NULL `ai_agent`.

**Why first:** it is the only phase that improves correctness *today*, and it
makes every later phase safe to run without fear of the inference path leaking.

### Phase 1 — Promote the two adapters that are already built — **S each**

`gemini-cli` and `kilo-code` have real, installable packages whose bin names
match `adapter.rs`'s `ExecutableDetection` exactly, and real automated setup code
(`configure_gemini` / `configure_script` in `ai_setup.rs`) that has simply never
been run against the real tool.

| Adapter | Package | Bins | Setup code |
|---|---|---|---|
| gemini-cli | `@google/gemini-cli` | `gemini` | `configure_gemini` → `gemini extensions install <bundle>` |
| kilo-code | `@kilocode/cli` | `kilo`, `kilocode` | `configure_script` → bundle `installer/install.sh` |

Run the §6 promotion checklist against each. Expect to find real bugs — every
prior live run in `VERIFICATION.md` did (the Claude `structuredPatch`-empty bug,
the Codex multi-file split). Budget for fixing, not just confirming.

**Blocked on:** nothing. Both installable right now; neither is on this machine.

### Phase 2 — Cursor, via its real hook API — **M**

Cursor ships a documented hook system: `~/.cursor/hooks.json` (user-wide) or
`.cursor/hooks.json` (project), with an `afterFileEdit` event whose payload
carries `file_path`. AtoAxis's `cursor` adapter already targets exactly this
shape (`ConfigHookBlock`, marker `atoaxis`, schema `afterFileEdit-v1`) — written
from public docs, never run.

- **P2.1** Install Cursor, capture a real `afterFileEdit` payload, diff it
  against the assumed shape.
- **P2.2** Fix the adapter + emitter to the real shape; confirm the event names
  Cursor as the agent and carries usable line counts (if `afterFileEdit` gives no
  line delta, decide whether to pair it with the before/after snapshot path
  already used for shell tools rather than inventing a count).
- **P2.3** Promote to `Verified` with evidence.

**Why high value:** Cursor is one of the most-used AI editors and WakaTime
demonstrably does not attribute it (#483). This is the first place AtoAxis would
be strictly better than the reference product rather than catching up.

### Phase 3 — Editor-extension agents via transcript parsing — **L**

Cline, Roo Code, Continue: no hook API, but each keeps its own task/conversation
history on disk. One parser each, implementing the existing `AiActivityParser`
trait so cursors, dedup and delivered-event state come for free.

Per agent: locate + document the storage location and record shape → commit a
fixture derived from a real session → parser + tests → live run → promote.

- **P3.1** Survey first, build second. Spend the first slice purely confirming
  each agent actually persists per-edit records with file paths (not just prose
  chat logs). **If an agent only logs conversation text, it is not reachable
  accurately and should stay `Unverified` — say so and stop.** This survey is the
  real gate on whether Phase 3 is one adapter or three.
- **P3.2..P3.4** One adapter per agent, in whatever order P3.1 says is cheapest.

**Why after Cursor:** higher uncertainty (storage shapes undocumented and prone
to change between releases), and the survey may legitimately kill part of it.

### Phase 4 — Remaining CLI agents — **S each, once the pattern is proven**

OpenCode, Goose, Copilot CLI (WakaTime ships
[copilot-cli-wakatime](https://github.com/wakatime/copilot-cli-wakatime), so a
hook surface exists). Mechanically identical to Phase 1; do them after Phase 1
has shaken the bugs out of the shared setup path.

`kimi-code-cli` and standalone `deep-code` stay parked: no confirmed public
integration point exists for either, and WakaTime does not support them either.
Revisit only if one ships a hook API.

### Phase 5 — Decide the fate of the inference stack — **S to decide, M to remove**

Once verified coverage is broad, `CorrelationEngine` + filesystem observer +
process observer + the Phase 8 broker wiring are dead code in production by
policy. Three honest options, to be chosen *then*, with coverage data in hand:

1. **Keep as diagnostics-only** — useful for "you have an agent running with no
   adapter installed, here is a setup prompt", which is a real product feature
   and does not attribute anything.
2. **Delete** — smallest surface, least confusion, loses the shadow corpus.
3. **Keep dormant** — status quo; costs nothing at rest but keeps ~2k lines and
   a duplicate worktree branch alive as a standing "is this on?" question.

Option 1 is the likely answer — it turns the inference work into onboarding
rather than attribution — but do not decide it in advance of Phase 1–3 data.

## 5. Ordering summary

```
P0 (enforce line)  ──┬──> P1 (gemini, kilo)  ──> P4 (opencode, goose, copilot-cli)
                     │
                     ├──> P2 (cursor)            <- differentiator
                     │
                     └──> P3.1 survey ──> P3.2-4 (cline, roo, continue)
                                                   │
                     P5 (fate of inference) <──────┘
```

P0 gates nothing technically but should land first; P1/P2/P3.1 are independent
and parallelisable; P5 needs P1–P3 results.

## 6. Promotion checklist — what `Verified` costs, per adapter

This repo already enforces a real bar (see `ai/VERIFICATION.md`: every promotion
records an actual run, and every prior run surfaced a real bug). Codifying it so
each phase above has the same definition of done:

1. Real tool installed, real version recorded.
2. `wakaclock ai setup <agent>` run for real; result is `configured`, not
   `not_detected`.
3. A real edit made by the real agent produces an event in
   `~/.wakaclock/ai-events.jsonl` naming that agent.
4. The event reaches the broker inbox and is `processed`, not dead-lettered.
5. The resulting row is inspected in ClickHouse with correct `ai_agent`,
   `actor_type`, path and line counts.
6. Re-run is idempotent — no duplicate heartbeat for the same edit.
7. Multi-file edit produces the correct number of events (the Codex bug class).
8. `Verification::verified(<timestamp>, "<tool version>")` set in `adapter.rs`,
   with the run written up in `VERIFICATION.md` — including any bug found.

Anything short of all eight stays `Scaffold`. A fixture is not a live check —
that rule predates this plan and should survive it.

## 7. What not to do

- **Do not attribute from the VS Code extension by watching document changes.**
  That is exactly the wall WakaTime hit (#476/#483); the API does not expose the
  authoring extension. It is also inference by another name.
- **Do not promote an adapter because setup exited 0.** `configured` proves the
  installer ran, not that the payload shape is right. Steps 3–7 are the point.
- **Do not widen correlation windows to catch more edits.** That trades precision
  for recall, which is the direction this decision just rejected.
- **Do not delete `ai_inferred` / `unknown` from the data model.** Historical and
  shadow rows use them; Phase 0 makes them safe, Phase 5 decides their future.
